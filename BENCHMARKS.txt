Qraven Build Performance Benchmarks
=====================================

Project under test: quarkus-renarde (20 modules, ~140-290 deps per module)
Machine: 1 CPU, 31GB RAM, Linux (Fedora)
Thread count: 1 (single-threaded builds for fair comparison)

All times are wall-clock, measured with multiple runs to reduce variance.
Dependency resolution (Aether) is done ahead of time and excluded from
qraven build times.

Build Modes Compared
--------------------

  Mode                              Time      Notes
  --------------------------------  --------  -----------------------------------------
  mvn clean install -DskipTests     ~28s      Includes 9s docs + 7s integration test
                                              module we skip; effective ~20s for the
                                              modules qraven builds. Excludes Aether
                                              resolution (~23s) since qraven does that
                                              ahead of time.

  qraven JVM (JDK 25)              ~15s      java -jar build.jar
  qraven JVM + AOT cache (JDK 25)  ~11s      java -XX:AOTCache=build.aot -jar build.jar
  qraven native (GraalVM 21)        ~2.5s    ./build-native (36MB binary)
  qraven native + warmup            ~1.4s    ./build-native with classpath pre-loading

How Each Mode Was Measured
--------------------------

mvn:
  $ mvn clean install -DskipTests
  Measured total time from mvn output. Run 3 times, middle value reported.

qraven JVM baseline (JDK 25, no AOT):
  $ /usr/lib/jvm/java-25/bin/java -jar target/qraven/build.jar
  Three runs: 15730ms, 15092ms, 14753ms. Median: ~15s.

qraven JVM + AOT cache (JDK 25, JEP 483 + JEP 515):
  Training (one-time):
    $ java -XX:AOTCacheOutput=target/qraven/build.aot -jar target/qraven/build.jar
    Produces a 33MB .aot file containing pre-loaded/linked classes and
    JIT method profiles.
  Production:
    $ java -XX:AOTCache=target/qraven/build.aot -jar target/qraven/build.jar
  Three runs: 10865ms, 11222ms, 11632ms. Median: ~11s.
  ~30% faster than baseline JVM. Improvement comes from skipping class
  loading/verification and having JIT profiles ready at startup.

qraven native (GraalVM CE 21, no classpath warmup):
  Build (one-time, ~13 min):
    $ native-image -jar build.jar build-native \
        -H:+UnlockExperimentalVMOptions \
        -H:IncludeResourceBundles=com.sun.tools.javac.resources.compiler,\
          com.sun.tools.javac.resources.javac,\
          com.sun.tools.javac.resources.ct,\
          com.sun.tools.javac.resources.launcher
    Produces a 36MB standalone binary. Embeds the entire JDK compiler.
  Production:
    $ JAVA_HOME=/path/to/jdk ./build-native
    Requires JAVA_HOME pointing to a JDK with lib/ct.sym (for --release).
  Three runs: 2582ms, 2540ms, 2500ms. Median: ~2.5s.
  ~83% faster than baseline JVM. Zero JVM startup, pre-compiled native
  code, no JIT warmup.

qraven native + classpath warmup:
  Same binary as above. Warmup pre-loads all 415 classpath JARs into
  OS page cache before compilation starts.
  Warmup: ~210ms. Build: ~1170ms. Total: ~1380ms.
  Three runs: 1376ms, 1382ms, 1355ms. Median: ~1.4s.
  44% faster than native without warmup, 20x faster than mvn.

  How warmup works:
  At startup, a temporary StandardJavaFileManager opens all unique
  classpath JARs by calling:
    fm.setLocation(StandardLocation.CLASS_PATH, allJars);
    fm.list(StandardLocation.CLASS_PATH, "", ..., false);
  This forces javac's internal getContainer() to open each JAR as a
  ZipFileSystem and walk its directory tree to build the package index.
  When the temporary file manager is closed, the ZipFileSystems are
  released, but the JAR file data stays in the OS page cache. When
  per-thread file managers later open the same JARs, the file I/O
  is served from RAM, and ZIP central directory parsing is faster
  because the data is already in CPU cache.

Key Technical Details
---------------------

Native image requires --release N (not -source/-target) in javac options.
Reason: GraalVM native images can't use the JRT filesystem to read
platform classes from lib/modules. The --release flag makes javac use
ct.sym (a plain ZIP) instead, which works in native images.

The build.jar uses javax.tools.JavaCompiler API with per-thread
StandardJavaFileManager instances (not thread-safe, so one per thread).
The file manager caches JAR indexes (ZIP central directories) across
compilations within the same thread.

JVM AOT (JDK 25, Project Leyden):
Uses JEP 483 (AOT Class Loading & Linking) and JEP 515 (AOT Method
Profiling). Does NOT pre-initialize objects or snapshot the heap like
GraalVM native-image. It caches loaded/linked class metadata and JIT
method profiles. The cache is tied to the exact JDK version, OS, CPU
architecture, and classpath used during training.

Where Time Goes
--------------------------

JVM mode: javac compilation is ~88% of total build time. The first
module takes longest (~10s) due to javac warmup (JIT compiling javac
itself). Subsequent modules are much faster (50-500ms each) once javac
is warm and JAR indexes are cached.

Native mode: no JVM startup or JIT warmup. The main costs are:
  - Classpath warmup: ~210ms (opening 415 JARs, building package indexes)
  - First module compilation: ~200ms (ct.sym loading + actual compilation)
  - Subsequent modules: 35-130ms each (pure compilation)

The native binary eliminates both JVM startup and javac warmup, making
JAR index loading and actual compilation the dominant costs.

Optimization Attempts (native mode)
------------------------------------

1. --initialize-at-build-time for JDKPlatformProvider
   Tested: --initialize-at-build-time=com.sun.tools.javac.platform.JDKPlatformProvider,
           com.sun.tools.javac.jvm.Target
   Result: REJECTED. Builds successfully but bakes in build-time JDK's ct.sym
   state. When JAVA_HOME points to a different JDK version at runtime, the
   class file versions in ct.sym may not match the embedded javac's expected
   versions (e.g., JDK 25 ct.sym has version 69.0 but GraalVM 21 javac
   expects max 65.0). The savings from pre-populating SUPPORTED_JAVA_PLATFORM_VERSIONS
   are negligible (<1ms).

2. ct.sym page cache warmup
   Added: Open ct.sym as ZipFileSystem during warmup, walk directory entries,
   then close. This primes the OS page cache for subsequent ct.sym opens by
   javac's --release processing.
   Result: ADOPTED. Adds ~15ms to warmup. Each getTask() call with --release
   still reopens ct.sym (creating a new ZipFileSystem), but the central
   directory data is already in page cache, making the open faster.
   Measured getTask per module: 15-40ms (first module: 46-66ms).
   Total getTask overhead across 15 modules: ~350ms.

3. Platform cache (extract ct.sym .sig files to temp dir as .class)
   Tested: Extract 5570 .sig files from ct.sym for release 17, rename to .class,
   write to temp directory. Set SYSTEM_MODULES directly on file manager,
   bypassing --release entirely.
   Result: REJECTED. Extraction takes ~2000ms (I/O-bound: 5570 files, 61 modules).
   This exceeds the ~350ms getTask savings. Only viable for projects with 100+
   compilable modules where the getTask savings outweigh the extraction cost.

4. ForwardingJavaFileManager wrapping for .sig files
   Investigated: Keep ct.sym ZipFileSystem open (no extraction), wrap the
   standard file manager with .sig→.class translation.
   Result: NOT IMPLEMENTED. ForwardingStandardJavaFileManager doesn't exist
   in JDK 21, and javac internally casts file managers to StandardJavaFileManager.
   A manual wrapper implementing StandardJavaFileManager is complex (~15 delegate
   methods). Would save ~350ms per build but adds fragile internal-API dependency.

5. ZipFileSystem survival across native-image build
   Investigated in Quarkus codebase: GraalVM explicitly resets
   ZipFileSystemProvider.filesystems via @RecomputeFieldValue(kind=NewInstance).
   This prevents any ZipFileSystem from surviving native-image build into the
   runtime image heap. Quarkus also marks filesystem providers for runtime-init.
   Result: NOT POSSIBLE. By design, ZipFileSystem instances cannot be baked
   into native images.

Key insight: the ct.sym per-compilation overhead (~25ms/module × 15 modules = ~375ms)
is ~15% of the native build time (~2.5s at base clock). The simplest optimization
(page cache warmup, 15ms cost) gives the best cost/benefit ratio.


Quarkus Build Performance (1438 modules)
=========================================

The sections above cover the small-project (quarkus-renarde) benchmarks. The
sections below cover optimizations for the Quarkus monorepo itself (1438 modules,
~2600 managed dependencies, 200+ extensions).

Qraven has two phases: generate (POM parsing + dependency resolution → build.jar)
and build (compilation + packaging). Both phases have been heavily optimized.


Generate Phase Optimizations
-----------------------------

The generate phase parses all pom.xml files, resolves dependencies via Maven
Resolver (Aether), scans extension JARs, and emits one Java source file per
module. It runs once when POMs change.

1. Dependency resolution caching
   Problem: Many modules share the same external dependencies. Without caching,
   Aether re-resolves the same artifact graph for every module.
   Fix: Cross-module resolution cache keyed on (groupId:artifactId:version,
   managedDeps hash). Compile and test caches tracked separately.
   Result: ~80 compile cache hits / 463 misses, ~208 test cache hits / 435 misses
   on the Quarkus build. Roughly 30% of resolutions served from cache.

2. Test-only dependency resolution
   Problem: Test classpath = compile classpath + test-only deps. Resolving the
   full test classpath redundantly re-resolves all compile deps.
   Fix: Compute test-only deps (deps with test scope not already in compile
   classpath), resolve only those, then merge with the cached compile result.
   Result: Most modules have 0-10 test-only deps vs 100-200 compile deps.
   Reduces Aether calls significantly.

3. Batch test dependency resolution
   Problem: Even with test-only filtering, each test dep was resolved in a
   separate Aether call.
   Fix: Batch all test-only deps for a module into a single CollectRequest
   with multiple dependencies.
   Result: One Aether call per module instead of N (where N = test-only dep count).

4. Managed dependencies conversion cache
   Problem: Converting Maven Model Dependency objects to Aether Dependency
   objects for 2600+ managed deps is repeated for every module.
   Fix: Cache the converted managed dependency lists. 18 distinct sets cover
   all 1438 modules (most modules inherit the same parent/BOM chain).
   Result: Managed deps conversion done 18 times instead of 1438 times.

5. Reactor module filtering from managed deps
   Problem: The Quarkus BOM contains all 1438 reactor modules as managed deps.
   Passing them to Aether is wasteful since reactor modules are tracked
   separately.
   Fix: Filter reactor GAs from managed dependency lists before passing to
   Aether. Reduces managed deps from ~2600 to a few hundred external artifacts.
   Result: Smaller dependency graphs, faster collection.

6. ReactorWorkspaceReader (eliminating remote snapshot lookups)
   Problem: Reactor modules use version 999-SNAPSHOT. When encountered as
   transitive dependencies, Aether checks all remote repositories for
   snapshot metadata (maven-metadata.xml). With 3 remote repos and hundreds
   of reactor modules appearing transitively, this caused 1860 remote HTTP
   requests — all failing (reactor modules don't exist in remote repos).
   This alone added ~167s to the generate phase.
   Fix: Register a WorkspaceReader on the Aether session that recognizes
   reactor module GAs and resolves them directly from the local repository.
   Aether's WorkspaceReader is consulted before any remote repository — the
   same mechanism Maven's own ReactorReader uses.
   Result: 1860 remote transfers → 4 (only non-reactor external artifacts
   checked on Confluent/Gradle repos). Generate phase time dominated by
   POM parsing and local resolution, not network I/O.

   Evolution of the fix:
   - First attempt: DependencySelector that excluded reactor GAs from transitive
     deps. Broke annotation processor resolution (CapabilitiesConfig not found).
   - Second attempt: Separate apSession without the selector for AP resolution.
     Fixed AP but 36 remote lookups remained for AP transitive reactor deps.
   - Third attempt: Added WorkspaceReader to apSession. Down to 4 transfers,
     but the selector still excluded transitive reactor deps needed by test-jars
     (9 test compilation failures).
   - Final fix: WorkspaceReader on main session, selector removed entirely.
     Zero correctness issues, 4 transfers. The workspace reader is strictly
     better — it prevents remote lookups without altering the dependency graph.

7. Pre-computed extension maps
   Problem: Scanning all runtime dependency JARs for
   META-INF/quarkus-extension.properties at build time is slow.
   Fix: Move extension JAR scanning, codegen tool version scanning, and AP
   cacheability checks to generation time. Store results in the generated
   Java source files as hardcoded constants.
   Result: Build time has zero JAR scanning overhead.

8. Parallel POM parsing and resolution
   Problem: Sequential POM parsing and dependency resolution for 1438 modules.
   Fix: Parallelize module scanning and dependency resolution across threads.
   Result: Generation uses all available CPUs for POM parsing.
   Note: An earlier attempt to merge POM parsing into the resolve phase caused
   a 4x slowdown and was reverted — the phases must remain sequential because
   resolution depends on the full reactor module set being known.


Build Phase Optimizations
--------------------------

The build phase compiles Java/Kotlin sources, copies resources, generates
indexes, creates JARs, and installs artifacts. It runs on every build.

1. AP classloader caching
   Problem: Each module compilation creates a new classloader for annotation
   processors. The quarkus-extension-processor is used by ~200 extension modules
   and loading it fresh each time is expensive.
   Fix: Cache the AP classloader for quarkus-extension-processor (which is
   side-effect-free and safe to reuse). Use fresh classloaders for other APs
   that may have state.
   Result: AP classloader created once, reused ~200 times. Non-cacheable AP
   modules use a ForwardingJavaFileManager to isolate the AP classpath.

2. Kotlin JIT warmup
   Problem: The Kotlin compiler (K2) is slow on first invocation due to JIT
   compilation. With ~60 Kotlin modules, the first few compilations are
   disproportionately slow.
   Fix: Run a throwaway Kotlin compilation of a trivial file during startup
   (before any module builds). This warms up the JIT compiler for the K2
   pipeline. Based on flamegraph analysis, the warmup targets the hot paths
   in the Kotlin frontend and backend.
   Result: First real Kotlin module compiles at near-steady-state speed.
   Warmup is skipped when no Kotlin modules are in the build.

3. Critical-path module scheduling
   Problem: With parallel builds, thread scheduling is FIFO by default. Modules
   on the critical path (most dependents) may start late, delaying the overall
   build.
   Fix: Prioritize modules with the most transitive dependents when scheduling.
   Result: Critical-path modules (quarkus-core, arc, etc.) start early,
   reducing idle time in later build stages.

4. In-process javac and Kotlin compilation
   Problem: Maven forks external javac and kotlinc processes.
   Fix: Use javax.tools.JavaCompiler API (in-process) and K2 JVM compiler
   API (in-process). Per-thread StandardJavaFileManager instances (not
   thread-safe). File manager caches JAR indexes across compilations within
   the same thread.
   Result: Zero process fork overhead. JAR index (ZIP central directory)
   cached across modules on the same thread.

5. Test source compilation
   Problem: Test sources need their own classpath (compile classpath + test
   deps + test-jar deps). Resolving and compiling test sources must not block
   the main build pipeline.
   Fix: Test compilation runs as a separate async stage after main compilation
   and JAR installation complete. Test dependencies wait on mainBuildDone
   (not buildFuture) to avoid deadlocks. Test reactor deps are tracked
   separately and resolved against the local repository.
   Result: Test compilation overlaps with other modules' main compilation.
   No deadlocks, no thread pool exhaustion.
